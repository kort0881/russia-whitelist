# Двухзвенный релей под режим IP + SNI

Схема для случая, когда оператор проверяет и адрес, и имя домена: клиент подключается к входу с «белым» адресом,
а вход передаёт трафик на зарубежный выход, который и выпускает в интернет.

```
клиент ──(VLESS/Reality, SNI из белого списка)──► вход (IP из белой подсети)
                                                     │
                                                     └──(VLESS/Reality, закрытый канал)──► выход (за рубежом) ──► интернет
```

Зачем два звена: вход виден оператору, и он должен быть разрешённым; выход скрыт, поэтому его адрес может быть
любым. Менять выход можно без изменения конфига у пользователей.

## Что нужно

| Роль | Требование | Комментарий |
|---|---|---|
| вход | IP в разрешённой подсети | проверяется `tools/wlcheck.py` |
| вход | домен и сертификат для TLS-варианта | либо Reality с разрешённым SNI |
| выход | любой зарубежный сервер | Reality, без домена |
| оба | Xray одной мажорной версии | расхождение версий даёт неочевидные ошибки |

## Шаг 1. Выход

Ставим Xray и поднимаем Reality-инбаунд (`tools/install-reality.sh` или вручную по
[`vps-reality-setup.md`](./vps-reality-setup.md)). Запоминаем:

- адрес и порт выхода;
- публичный ключ Reality (`pbk`), shortId (`sid`), SNI, который использует выход;
- UUID клиента, который будет ходить с входа на выход.

Проверка: `xray -test -config /usr/local/etc/xray/config.json`, затем `systemctl restart xray` и
`systemctl is-active xray`.

## Шаг 2. Вход

На входе нужны два инбаунда:

1. **клиентский** — то, к чему подключаются люди: VLESS + Reality (или VLESS + TLS + XHTTP за разрешённым CDN),
   SNI обязательно из белого списка;
2. **служебный** — не нужен, если вход и выход соединяются аутбаундом (см. ниже).

Маршрутизация: клиентский инбаунд отправляет всё в аутбаунд на выход.

```json
{
  "inbounds": [{
    "port": 443,
    "protocol": "vless",
    "settings": {
      "clients": [{ "id": "UUID-КЛИЕНТА", "flow": "xtls-rprx-vision" }],
      "decryption": "none"
    },
    "streamSettings": {
      "network": "tcp",
      "security": "reality",
      "realitySettings": {
        "dest": "ДОМЕН-ДОНОРА:443",
        "serverNames": ["ДОМЕН-ДОНОРА"],
        "privateKey": "ПРИВАТНЫЙ-КЛЮЧ-ВХОДА",
        "shortIds": ["SHORT-ID-ВХОДА"]
      }
    }
  }],
  "outbounds": [{
    "protocol": "vless",
    "settings": {
      "vnext": [{
        "address": "АДРЕС-ВЫХОДА",
        "port": 443,
        "users": [{ "id": "UUID-КЛИЕНТА", "encryption": "none", "flow": "xtls-rprx-vision" }]
      }]
    },
    "streamSettings": {
      "network": "tcp",
      "security": "reality",
      "realitySettings": {
        "serverName": "SNI-ВЫХОДА",
        "publicKey": "PBK-ВЫХОДА",
        "shortId": "SID-ВЫХОДА",
        "fingerprint": "chrome"
      }
    }
  }]
}
```

Шаблон с плейсхолдерами — [`../configs/vless-relay-server.json`](../configs/vless-relay-server.json).

## Шаг 3. Сквозная проверка

Проверять надо не «подключилось», а куда именно вас выпустило:

```bash
# на клиенте, через поднятый туннель
curl -s https://ifconfig.me     # должен вернуть адрес ВЫХОДА, а не входа
```

Если вернулся адрес входа — аутбаунд не применился (ошибка в конфиге, лишний `freedom` первым в списке).

## Шаг 4. Эксплуатация

- **Слепок перед правкой.** Скопируйте рабочий `config.json` в `config.json.bak_$(date +%F)` — откат одной командой.
- **Никаких рестартов в рабочие часы**, если есть живые пользователи: соединения рвутся.
- **Логи.** `loglevel: warning`, access-log выключен: иначе адреса клиентов пишутся на диск.
- **Проверка по расписанию.** Раз в сутки: жив ли вход, разрешён ли его IP, отвечает ли выход.
- **Ротация ключей** — только осознанно: смена ключа Reality или UUID ломает уже выданные клиентам ссылки.

## Ограничения схемы

- Требует двух серверов и обслуживания — это дороже и сложнее, чем SNI-спуфинг.
- Если вход потерял «белый» адрес, схема падает целиком: нужен резервный вход.
- Полный блэкаут (не работает даже Госуслуги) не обходится никакой схемой — канала физически нет.
